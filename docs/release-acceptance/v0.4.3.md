# OneCode 0.4.3 acceptance

Windows x64 validation on 2026-10-21–22: **309 focused tests passed**, with **0 failures and 0 skips** across 12 files. Public verification, TypeScript, privacy, notices, production build, package isolation and packaged native runtime smoke passed. This is a focused run, not a repeat of the complete 10,000+ test suite. Dependencies are unchanged.

The installed 0.4.2 desktop and laptop logs reproduced Connected/Checking flapping. Native startup and route configuration completed within seconds, but the public check repeatedly failed. A desktop diagnostic received valid exact metadata and MCP initialize replies in approximately five to eight seconds, beyond the previous four-second request deadline. Loopback initialize completed in about 40 ms. A later three-round comparison found both old and corrected probes ready once network latency improved; that comparison does not establish a permanent upstream network fix.

The source correction retains a four-second DNS budget, allows twelve seconds per pinned public request and bounds the full parallel check to thirty seconds. Slow reads are reported as timeouts rather than a proved TLS failure. Hostname/certificate verification, public-address restrictions, exact metadata, MCP reply checks, caller cancellation and native route custody remain required.

The hotfix updater is a Windows application-only path. It reuses the existing publisher, release checksum verification, explicit install intent, active-work fences, shutdown and visible relaunch owners. A compatible capsule preserves the installed native runtime. An incompatible runtime uses a complete installer when available. Profile state is excluded. Automatic in-process code replacement, unsigned third-party patch sources and termination of an unconfirmed running successor are not supported.

## Internal updates and actual hotfix activation

The update owner tests selected a compatible application capsule and handed it through the explicit install flow; an incompatible native fingerprint, including a changed Electron version, selected the ordinary installer. Existing busy-work, cancellation and version fences remain covered. The source retains normal three-part version 0.4.3, matching installer metadata and file version 0.4.3.0 so the shipped 0.4.2 updater can discover and install this enabling release.

An isolated copy of the final packaged application was given a marked fixture hotfix representing 0.4.4. The production staging owner ran twice inside actual Electron, proving both fresh and already-staged ASAR writes use raw filesystem semantics. The detached helper applied the snapshot; the actual packaged Electron process loaded its canary, logged application version 0.4.4, kept a loaded visible window alive and exited cleanly. Its native inventory matched before and after. The fixture preserved every unpacked native byte, used a separate profile and random bridge port, and suppressed login/protocol registration changes. Registration and shortcut checks were mocked because this copy was deliberately unregistered. This proves application activation, not installation on the user's laptop or publication of 0.4.4.

Rollback tests restored the previous snapshot after a failed launch. Another test retained both the new files and rollback backup when a successor remained running but unconfirmed, without killing it or overwriting its loaded files. Traversal, Windows reserved paths, case aliases, unexpected ZIP entries, altered checksums, incompatible architecture and changed native files were refused. A protected installation falls back to the ordinary installer path. Power-loss recovery during replacement is not claimed automatic; the rollback copy or a full installer remains the recovery path.
