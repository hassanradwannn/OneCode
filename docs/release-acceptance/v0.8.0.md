# OneCode 0.8.0 verification scope

This record separates source-level implementation, automated regressions, native observations, cloud packaging and installed acceptance. Publication receipts are added after the release jobs finish. It does not treat a picker observation or an inserted draft as a delivered task.

## Automated source checks

Focused local regressions cover:

- Three-provider conversation identity and URL routing, namespace collision refusal, independent sign-in/trust and durable settings across switches and stale saves.
- Dynamic current/legacy model groups, descriptions, exact per-model efforts and native cost labels in Desktop and Remote; isolated provider catalogs and discovery nonces; restoration without browser-opening authority.
- Current-model/current-effort labels for the added provider before and after discovery, with no implicit first-model/High selection; a lost discovery page permits a fresh explicit inspection while rejecting late results from its spent nonce.
- Read-only ordinary refresh versus a nonce-scoped explicit single-model control request; unknown metadata stays distinct from an observed absent control. Desktop, settings and Remote render only observed native labelled levels or binary switches, retain current-setting intent without assuming Off, and hide absent/unknown control panels. Provider catalogs preserve that metadata through restart. All observed model rows remain available without copied controls, and late results for a previous selection are ignored.
- Actual authenticated loopback API discovery and provider controls, both routing aliases, ordinary outbox admission, canonical final-response projection, IDE thread affinity and conflicting provider refusal.
- Independent MCP endpoints and local capability ledgers, exact task/ACK/turn admission, foreign/revoked/pending proof, restart recovery, worker/files/workspace contracts and retained terminal custody.
- Stored-chat opening/readiness and Goal/Loop objectives, switches and exact pending obligations after restart, including namespaced provider identities.
- Native account-limit presentation, unknown or malformed reset evidence, one notification per episode and separation from history retry deadlines. These checks grant no replay authority.
- Embedded selected-provider Show/Sign-in, same-opener auth routing, refusal to borrow an unrelated shared auth page and provider-scoped paired sign-in observations. The preserved legacy cookie-transfer fixture policy stays separate from normal production sign-in.
- Optional native skill export and explicit opt-in, including all configured browser choices; raw Markdown and uploadable ZIP guidance remain distinct.
- Compact/full native-skill variants remain frozen under one original task capability and authored input; an unconfirmed native skill cannot supply compact-delivery proof. These checks do not establish that a skill was installed in a real account.
- Component compilation and artifact preview bounds, local module resolution, bundled React/Tailwind/Lucide/Recharts, offline Mermaid and existing network-closed Desktop/Remote document envelopes. Source remains available when compilation or a package import fails.

The development suite is intentionally local and unpublished. Public `npm run verify` checks source prerequisites, privacy, notices, TypeScript and production bundles. GitHub builds from the frozen source and runs platform packaging, native compatibility and packaged runtime smoke before release finalization.

## Native inspection and acceptance

Windows menu and DOM observations use the installed CUA Driver CLI and the signed-in native browser. The observed free account exposes native selectable models alongside Upgrade entries, legacy and Effort submenus, and provider-specific composer controls. Account-visible rows supply evidence; screenshots are not a hard-coded subscription catalog.

The supplied connector screenshots are used in the selected-provider setup guide. They show the custom-connector action and empty Name/MCP server URL form, without installation secrets.

Full native task-lifecycle evidence is recorded separately as it is exercised. This source record alone does not certify native Send, upload, Stop/Steer, local-tool invocation, final capture, generated-file import or installed update acceptance.

An isolated Windows candidate has proved fresh native opening, one exact app-authored Send, UUID-bound ACK/history and capture of a five-byte `READY` final with a completed turn. No local tools ran in that check. It used a separate profile, bridge and read-only QA workspace; the production installation was preserved. A separate native skill check uploaded the public bundle, selected `/onecode` into the editor's native `data-skill-id="onecode"` chip, sent one harmless request and received `READY`. The earlier name containing the service's reserved word was rejected; the shipped skill name and ZIP root are now `onecode`.

The first enabled-connector read task reached its exact native question and history but stalled before any recorded tool call or final. It was preserved without Send/Retry replay. A rebuilt candidate added bounded transport-stage diagnostics, excluding arguments, credentials and provider request identifiers. A separate newly authored read then proved the full path: one native Send and exact ACK/question, capability admission in 5 ms, an approved read response in 70 ms, the exact marker in the captured final and a completed turn. The full native turn took 34.1 seconds. These diagnostics distinguish waiting before a request arrives from receipt admission and SDK dispatch; they do not establish the cause of the earlier provider-side wait.

The `READY` messages above are deliberately harmless verification prompts. Normal delivery sends the actual task directly. Optional native skill selection happens in the same protected composer; it does not send a readiness greeting or consume a preparatory model turn.

Native legacy-model inspection also confirmed an Extended checkbox with real checked/unchecked states, distinct from discrete effort levels. Its inert decorative switch is not the actionable control. Narrow native layouts render labelled inline Effort and More models groups; wide layouts expose submenus. Reasoning controls are advertised only after observing the selected model's actual control, with unknown and absent controls hidden.

Initial candidate diagnostics exposed model-inspection cancellation and an unnecessary native connector-preparation gate. The revised delivery contract reads model lists without cycling selections, marks unobserved per-model efforts explicitly, and treats account connector enablement as setup state rather than a per-message toggle/mention requirement. Local tool authorization retains its exact capability, native question, history and turn checks. These repairs need fresh native proof from the rebuilt candidate; an earlier rejected preparation is not a delivered task or a reason to replay one.

Fresh native openings, parallel claims and source/successor UUID joins are described in [browser conversations and local sessions](../PROVIDER-SESSIONS.md). Their fixture coverage does not substitute for native multi-chat and Compact & Resume acceptance.

## Remaining evidence limits

- Paid-account model discovery and quota exhaustion/reset have not been established by free-account menu inspection. Unknown reset information is preserved as unknown.
- Shared browser routing and the optional embedded host have source/fixture coverage; exhaustive signed-in acceptance is not claimed. Firefox adapter staging does not supply a signed distributable package. The existing Firefox availability/signing limitation remains; no unrelated project's extension is used as a substitute.
- Native Linux browser, full Desktop/Remote workflow and installed 0.8.0 updater acceptance require their own evidence. Windows source tests, WSL and cloud packaging do not substitute for that acceptance.
- Native artifact imports require the provider's exposed source viewer and exact ownership. Arbitrary third-party packages, external services, provider-only runtime APIs and unavailable original-media export are not local preview compatibility claims.
- A matched native runtime fingerprint and verified release manifest establish update compatibility, not successful installation or visible relaunch. Production installation/restart remains subject to the maintainer's manual-update instruction.
