# OneCode 0.5.2 candidate acceptance

Date: 2026-10-23. Canonical branch: `release`.

**Status: stable candidate not published; superseded after native Linux hotfix acceptance exposed a bootstrap filesystem defect.** Production sessions are outside the isolated acceptance profiles. The separate 0.5.2 Beta feed was returned to draft after the checks below.

## Inherited reliability checks

The 0.5.1 candidate record retains the earlier Stop, process custody, Compact & Resume, durable authorization, browser and updater regression scope. Final Windows and Linux 0.5.1 packages passed runtime smoke at source checkpoint `1e3cb8a`. Windows `verify:ci` also passed there. Refreshed Graphify reported 9,212 nodes and 29,282 edges with no invalid endpoints, duplicate edges or self-loops; 32 files had no extracted nodes and 7 had partial parses.

## Additional acceptance

- Connector naming and approval: 312 focused checks passed, including configured stable names with no suffix, Desktop, Legion and Unicode. A card naming Beta remained untouched when Setup named another connector.
- Native Gemini Flash 3.8 successfully auto-approved the exact configured connector for one read-only plugin-list call. Flash-Lite 3.5 selected a foreign saved connector in automated and fully manual comparisons; the Companion refused that foreign card. This does not claim correct routing by every Gemini model.
- Private Windows and Linux 0.5.0 Beta fixtures were built from current repaired code with version changes only. They are local test baselines, not historical official 0.5.0 builds. Both installed with their existing isolated profiles and displayed 0.5.0 Beta.
- In the installed Windows fixture, a fresh Gemini opening projected queued, then browser preparation, then attached to the native chat and displayed the exact tool-free response. Preparation status cleared without another Send.
- That probe exposed a false unattributed badge and global-policy menu on provisional desktop chats. Focused regressions failed before the repair and passed afterward for queued/browser openings; null or absent legacy origins retain the existing unattributed behavior. The repair reads the existing desktop origin and creates no execution authority. Remote already distinguishes these provisional rows.
- Eight release-highlight and exact stable/Beta release-note URL checks passed. TypeScript checks passed after these changes.
- Final renderer regressions at `8d2f072`: 147 passed. `verify:ci` passed at that checkpoint; Graphify reported 9,221 nodes and 29,295 edges with no invalid endpoints, duplicate edges or self-loops. Later updater changes require a fresh package and verification checkpoint.
- Windows installed full update passed from a private 0.5.0 fixture to public `beta-v0.5.1`. The internal helper waited for predecessor exit, verified installer exit and installed version, then confirmed one stable visible successor. All 80 original history files remained present; browser and connector name were retained. The app-managed Companion automatically updated from 0.5.0 to 0.5.1 and reconnected.
- The initial Windows manual fallback was an acceptance installation-context mismatch: registration written by the build-shell installer was absent from the normal desktop context. Reinstalling the identical fixture through the desktop launcher made all four registry queries succeed. The updater custody checks were preserved. A metadata timeout recovered through the existing retry; the private fixture's unpublished old blockmap required the verified full-installer fallback. This does not prove differential transfer.
- Linux native full-update testing downloaded and replaced the AppImage with the verified public 0.5.1 image, but automatic successor launch failed. An explicit native launch then loaded 0.5.1 with the original browser and connector settings. The automatic path remains a failed check pending the independent launch observer repair and a fresh native run.
- Ten focused release-highlight checks passed after making the installed dialog retain the Beta version label.
- At checkpoint `2cdc722`, `verify:ci`, packaged runtime smoke and both platforms' asset inventories passed. These checks did not detect the Linux layer-startup defect below.
- Installed Windows differential reconstruction passed from a private 0.5.0 fixture with an authentic matching installer/blockmap advisory cache. The reconstructed 203,219,911-byte public Beta 0.5.1 installer matched its published SHA-256. This was explicitly seeded-cache acceptance; the earlier unpublished-old-blockmap case correctly used full fallback. The fix makes the Generic GitHub feed use single-range requests, matching electron-updater's GitHub provider.
- Installed Windows compatible hotfix and combined base-plus-hotfix both passed to Beta 0.5.2. The combined helper installed the verified 0.5.1 base without relaunch, applied the capsule and confirmed one visible 0.5.2 successor. The compatible path retained the native runtime and confirmed its one visible successor. All 80 original history files remained present; Chrome and the configured connector suffix were retained. The managed Companion updated automatically and the release dialog displayed `0.5.2 Beta`.
- The repaired independent Linux handoff passed a fresh full update from a private 0.5.0 fixture to public Beta 0.5.1, confirming the visible successor and retained Brave/connector settings. Its temporary copied runtime was retired.
- The immutable public Linux Beta 0.5.1 activated a compatible 0.5.2 application layer but its older `app.relaunch` path produced no successor. The repaired private 0.5.0 combined path installed the correct public 0.5.1 base and launched once, but that base's bootstrap rejected the layer: Electron's patched filesystem reports `app.asar` as a virtual directory. The independent observer correctly recorded failure, never reported 0.5.2 ready and did not launch again. Both Linux hotfix checks are failures at this checkpoint. Correct raw filesystem semantics require a new full Linux base and a new runtime fingerprint.

The earlier combined native ChatGPT command-plus-generation probe was rejected by the provider before command execution and is not counted as a pass. Separate native per-process Stop and tool-free generation Stop passed as recorded in the 0.5.1 candidate record.
