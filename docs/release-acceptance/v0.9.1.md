# OneCode 0.9.1 — API/browser transport isolation

The reported API opening produced a native Gemini URL carrying the same outbox-style `cos-input` marker. Source inspection and an isolated regression reproduced the transport leak: a newly queued OpenRouter opening was published by `pendingBrowserInputs` before the API runner claimed it. The Companion's native fallback could interpret a non-browser provider as Gemini. Timing of browser polling versus API preparation explains why the unwanted opening appeared intermittently.

The outbox now refuses non-browser transport rows before native publication or claims and rechecks resolved conversation transport. The bridge's opening-lease projection excludes API rows. The Companion independently filters explicit API/unknown providers and unsupported conversation namespaces before tab operations. The API runner retains its original claim, exact receipt, task identity and tools; no permission or browser authority is fabricated.

Four default-provider regression cases failed against the previous implementation and pass with the repair. They cover an API opening while Gemini, ChatGPT, Claude or OpenRouter is selected, queued/reloaded/native-claim rejection, and successful API-owned claiming. Four focused tests execute the shipped Companion delivery owner with tab access instrumented; non-browser offers return before tab queries or creation. The authenticated real HTTP bridge test preserves an ordinary Gemini opening while excluding the concurrent API input from both native lists. Existing native opening and selected-chat cases remain part of the focused checks.

Validation and release receipts follow below. Tests and private evidence remain local/ignored. No production chat, browser tab, process, credential, profile or installed app is modified during maintenance. Existing limitations of the broader legacy bridge/native acceptance matrix remain as recorded in the Stable 0.9.0 acceptance document.
