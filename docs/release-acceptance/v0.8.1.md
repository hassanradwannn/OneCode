## Confirmed defect and repair

A native refresh during an existing generation can receive `{ok:false,status:0}` after a bridge connection reset. The recorder previously treated that as an application identity answer and released its reload gate. A production-content-script regression reproduced a second local generation for the existing user question. The repaired gate retains the original task until the durable turn can be adopted. Unreachable-worker and timeout cases, final capture after reconnect and stale failed-read epoch checks use the same owner. This repair does not relax capability/ACK/history/turn validation or replay a Send.

The Linux refusal timeline establishes that OneCode recorded a completed turn while the original disk command was still running, before the native final answer or any newer user question. The subsequent exact-task refusal therefore cannot be explained by the next question changing the key. A production-function regression reproduced acceptance of a historical completed footer; the repair requires the exact current native question and mounted current answer, including after a quiet-period verdict was cached. This is a confirmed defect and timeline, not proof that every prior refusal had the same cause.

Retained command 1637 was inspected read-only: it completed successfully, with complete unread output retained and no interrupted/truncated output. The command was neither rerun nor killed, and inspection did not acknowledge its output. Exact-task process-custody tests remain separate from that production observation.

The newly reported Linux connection drop coincided with a native network interruption and Tailscale coordination-server timeouts. The daemon remained active and cached HTTPS/Funnel capabilities and Linux operator authorization remained present, while native status reported the device offline. OneCode incorrectly labelled that read-only wait as a failed Funnel check. Source now projects a network wait, preserving machine-approval and genuine policy failures separately. This status repair does not itself repair Tailscale's external connectivity.
