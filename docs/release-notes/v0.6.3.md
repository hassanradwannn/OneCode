# OneCode 0.6.3

Stable application release carrying the **Experimental** local OneCode API after native CLion acceptance exposed and corrected OpenAI-client interoperability gaps. The application release is stable; the API itself remains opt-in, disabled by default and explicitly experimental in Settings.

- Fresh IDE chats no longer inherit a stale provider-bound API conversation. OneCode keeps separate recent IDE thread mappings and preserves the provider binding of every existing chat.
- JetBrains retrieval-subquery and chat-title housekeeping requests are answered locally instead of becoming durable OneCode turns, so they no longer occupy the single provider-completion lane or add provider latency.
- The durable OneCode session remains the history owner. IDE system/developer instructions and the current user/file attachment context are retained, while earlier assistant/tool transcript is not copied back into every turn.
- Different IDE projects map to different OneCode sessions. Client thread identifiers are used when available; project plus first-turn identity is the bounded fallback for clients that expose no stable thread id.
- When an IDE project is already approved in OneCode, the API binds its session to the normal OneCode project owner. The agent can then use direct filesystem read/patch/exec tools and CLion/PyCharm observe those file changes immediately. IDE metadata never grants a new filesystem root; unapproved projects fall back to the IDE edit/snippet format until the folder is approved once.
- IDE chat panes that cannot call OneCode-specific control URLs can send `/new` and `/provider chatgpt|gemini` as ordinary chat messages.
- Gemini completion waiting resolves the response turn through OneCode's canonical chronology, fixing the case where the exact final was already durable but the HTTP request remained open.
- The listener remains disabled by default, loopback-only and authenticated with the same OS-encrypted per-device key.

## Stable update path

0.6.3 is intended as an application-only stable capsule when the published stable base reproduces the same immutable runtime fingerprint. The previously pushed `beta-v0.6.2` tag is not rewritten. Stable publication must use a new `v0.6.3` tag and the normal internal updater feed; a runtime mismatch fails packaging instead of weakening compatibility.
