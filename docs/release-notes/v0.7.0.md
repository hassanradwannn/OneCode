# OneCode 0.7.0

This release brings the reliability repairs developed since Stable 0.6.17 into one Stable update:

- Explicit native Steer retains the original local process and its output while the new question receives its own exact task receipt. Preparing the next input preserves authorization for already admitted calls.
- Gemini model preparation follows its own native header/control replacements while preserving the selected model, draft and deadline. Native approvals match the configured connector and enabled tool names.
- Connection notices and silence warnings cannot end a running task. Companion restoration, composer text with connector chips and restart recovery retain their original delivery and task owners.
- Failed automatic-message notices can be dismissed without deleting delivery evidence. A later confirmed question clears an old failed-handoff composer badge while its saved summary remains available.
- Mermaid artifacts render offline with editable source and existing exports. Plugin discovery is redacted and bounded, with exact schemas retrieved separately.
- Compatible updates retain the installed native base, user profile and saved chats on Windows and Linux.

Durably saved browser observations now release the tab's control queue before their HTTP upload finishes. The original event reply still waits for its initial ordered delivery. Input claims, Send authorization and native acknowledgements can proceed while transcript transport is slow. An acknowledged input also releases its composer slot while later progress revisions continue draining.

Rendering reconciliation runs independently for each tab. A hung attachment, focus acknowledgement or release cannot block another chat's opening or input pickup. A bounded caller wait retains the original browser operation until its actual reply, so it cannot repeat an attachment or revive cancelled activity. Explicit Steer also retains its exact already-published source question when the provider virtualizes that row, under the same turn, conversation, document and final Send guards.

ChatGPT delivery receipts follow the new native question identity when its page reuses a section that previously held an identified question. Old message IDs, unidentified pre-existing sections, changed chats and nonmatching task text remain refused. This lets an accepted Steer receive its delivery acknowledgement and activate its task authorization instead of timing out after it was already sent.

If the preceding question's row has unmounted, explicit Steer can retain its already-published identity only for the exact current native generation or validated Fiber-owned section before the click. The old identity also remains a veto against mistaking its later rehydration for the new message.

Manual compaction can retain a completed source whose question bubble has unmounted only through a fresh, complete native frame and its matching locally recorded final. The source stays frozen through preparation and Send authorization; unknown or newer questions, changed chats, pending tools and new user Sends refuse it. Automatic compaction and live Stop receive no such fallback. The recorder-pair revision forces replacement of older adapters that lack the new receipt contract.

An exact app-owned Gemini tool-free warmup that stalls before receiving a conversation route can spend one page refresh. The existing command or opening retains the spent receipt, original deadline and paired browser/tab custody across replacement documents and app restart. A retained warmup must settle before the task continues. If the original document receives its real conversation while the refresh permit is pending, Main must adopt that exact document before the task continues.

Human drafts, attachments, native approvals, tools, changed accounts and foreign messages veto preparation recovery. A refresh supplies no authority to replay an uncertain task Send, change a connector or terminate a local process.

The replacement Gemini page retains that preparation while its editor loads or clears the already-submitted warmup text. It uses the original fixed deadline and still requires the exact warmup row, READY reply and empty writable editor before continuing the task.

If the refresh discarded the unrouted warmup and returned an empty home page, the exact adopted replacement may initialize once. Main durably spends that child attempt before its native click; repeated requests, lost replies and restarts cannot grant another initialization or refresh. The browser must prove the unchanged account and marker, empty writable idle editor and absence of user messages, responses, tools, approvals and files. The same original deadline and ordinary real-task binding, Send authorization and native acknowledgement remain required.

Native input events from the adapter's own synchronous initialization edits and Send-triggered editor clear retain that draft lease. Human edits during permission, readiness and receipt waits still revoke it. Waiting continuity accepts an incremental prefix of READY; final settlement still requires the complete exact reply, native idle state, empty writable editor and real conversation ID.

Release validation and native acceptance are recorded separately; source regressions alone do not certify an installed provider or updater path.
